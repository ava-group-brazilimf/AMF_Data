# Task: Classify Pipelines by Complexity

```yaml
task_id: classify-pipelines
agent: discovery-scout
version: "4.0"
command: "*classify"
phase: UPSTREAM
gate: 1
output: "classification.json"
output_folder: "projects/{project_name}/outputs/upstream/discovery/inventory/"
```

---

## Purpose

Classify every discovered pipeline by complexity using a multi-factor scoring algorithm. The classification drives effort estimation, migration sequencing, and resource allocation for downstream agents.

---

## Pre-Conditions

- [ ] `inventory.json` generated by `*scan-repo` task
- [ ] Pipeline details available (transformations, connections, scripts)
- [ ] Scoring weights configured (defaults used if not provided)

---

## Execution Steps

### Step 1 — Load Inventory

```
1.1  Load inventory.json from projects/{project_name}/outputs/upstream/discovery/inventory/
1.2  Extract all pipeline objects
1.3  Validate that pipeline metadata is complete
1.4  Log total pipelines to classify
```

### Step 2 — Apply Scoring Algorithm

For each pipeline, calculate complexity score based on:

```
2.1  Transformation Count (weight: 0.25)
     - 0-5 transformations   → score 1 (Simple)
     - 6-15 transformations  → score 2 (Moderate)
     - 16-30 transformations → score 3 (Complex)
     - 31+ transformations   → score 4 (Very Complex)

2.2  Language Diversity (weight: 0.15)
     - 1 language             → score 1
     - 2 languages            → score 2
     - 3+ languages           → score 3

2.3  Dependency Count (weight: 0.20)
     - 0-3 dependencies       → score 1
     - 4-8 dependencies       → score 2
     - 9-15 dependencies      → score 3
     - 16+ dependencies       → score 4

2.4  Custom UDFs/Scripts (weight: 0.25)
     - No custom code         → score 0
     - 1-2 UDFs               → score 2
     - 3-5 UDFs               → score 3
     - 6+ UDFs or inline code → score 4

2.5  Data Volume (weight: 0.15)
     - < 1 GB                 → score 1
     - 1-10 GB                → score 2
     - 10-100 GB              → score 3
     - 100+ GB                → score 4
```

### Step 3 — Calculate Weighted Score

```
3.1  weighted_score = Σ(factor_score × factor_weight)
3.2  Classify by weighted_score:
     - 0.0 - 1.0  → SIMPLE
     - 1.1 - 2.0  → MODERATE
     - 2.1 - 3.0  → COMPLEX
     - 3.1 - 4.0  → VERY_COMPLEX
3.3  Assign migration effort estimate:
     - SIMPLE       → 1-2 days
     - MODERATE     → 3-5 days
     - COMPLEX      → 1-2 weeks
     - VERY_COMPLEX → 2-4 weeks
```

### Step 4 — Generate Classification Report

```
4.1  Compile classification results into classification.json
4.2  Generate summary:
     - Count per complexity category
     - Total estimated effort
     - Top 10 most complex pipelines
     - Recommended migration sequence
4.3  Save to projects/{project_name}/outputs/upstream/discovery/inventory/classification.json
```

## PowerCenter — Mapeamento para o Algoritmo de Scoring

Quando `scan_metadata.platform == "Informatica PowerCenter"`, usar a seguinte
correspondência para alimentar o algoritmo existente:

| Campo do algoritmo | Fonte no objeto PowerCenter |
|---|---|
| Transformation Count | `mapping.transformation_count` |
| Language Diversity | Número de tipos distintos de Transformation na Mapping |
| Dependency Count | Shortcuts + Lookups + número de sources na Session |
| Custom UDFs/Scripts | Java Transformations + External Procedures + SQL Overrides |
| Data Volume | Estimado via `target_definition.estimated_rows` se disponível |

**Regra adicional:**
Qualquer Mapping com `has_java_transformation = true` ou `ExternalProcedure`
recebe `classification = VERY_COMPLEX` independente do score calculado.
Worklets e Mapplets herdam a complexidade da Mapping mais complexa que os utiliza.

---

## Generic Spark / Mixed Code — Mapeamento para o Algoritmo de Scoring

| Campo do algoritmo | Fonte |
|---|---|
| Transformation Count | Statements SQL + funções Python + transformações Spark no Scala |
| Language Diversity | Contagem direta de linguagens na cadeia (SQL/Py/Scala/Shell) |
| Dependency Count | Arestas do grafo incluindo FLAG_FILE, DATA_FILE e EXTERNAL |
| Custom UDFs/Scripts | Todo .py e .scala conta como custom code |
| Data Volume | Estimado por row counts se disponíveis; senão UNKNOWN |

**Regras adicionais:**
- Cadeia com `orchestration_type = IMPLICIT_FILESYSTEM` → mínimo COMPLEX
     (a fragilidade da orquestração é em si um fator de complexidade de migração)
- Presença de EXTERNAL dependency (linked server) → +1 nível
- 3+ linguagens na mesma cadeia → mínimo COMPLEX

## Azure Synapse — Mapeamento para o Algoritmo de Scoring

| Campo do algoritmo | Fonte |
|---|---|
| Transformation Count | Activities por pipeline + transformações por dataflow |
| Language Diversity | T-SQL + linguagens dos notebooks + expression language ADF |
| Dependency Count | ExecutePipeline aninhados + datasets + linked services |
| Custom UDFs/Scripts | Notebooks + WebActivities + custom activities |
| Data Volume | DIU/parallelism hints nas Copy activities se presentes |

**Regras adicionais:**
- Mapping Data Flow com 15+ transformações → COMPLEX
- Pipeline com ExecutePipeline aninhado 3+ níveis → COMPLEX
- CTAS com DISTRIBUTION = HASH → registrar coluna de hash (vira liquid
     clustering / ZORDER no destino; perda dessa informação degrada performance)
