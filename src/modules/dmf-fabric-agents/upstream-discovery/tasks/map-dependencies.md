# Task: Map Dependencies — Build Dependency Graph

```yaml
task_id: map-dependencies
agent: discovery-scout
version: "4.0"
command: "*map-dependencies"
phase: UPSTREAM
gate: 1
output: "dependency-graph.json"
output_folder: "projects/{project_name}/outputs/upstream/discovery/dependency-graphs/"
```

---

## Purpose

Build a complete Directed Acyclic Graph (DAG) of dependencies between all discovered objects. Parse imports, references, and data flows to understand how tables, pipelines, jobs, and scripts relate to each other. Detect circular dependencies and calculate graph metrics.

---

## Pre-Conditions

- [ ] `inventory.json` generated by `*scan-repo` task
- [ ] All pipeline/job metadata includes transformation details
- [ ] NetworkX or equivalent graph library available

---

## Execution Steps

### Step 1 — Load Inventory & Parse References

```
1.1  Load inventory.json
1.2  For each pipeline/job:
     - Parse SQL statements for table references (FROM, JOIN, INSERT INTO)
     - Parse import statements in scripts (Python, Scala, Java)
     - Parse configuration files for connection references
     - Parse orchestration definitions for job dependencies
1.3  For each table/view:
     - Identify upstream sources (who writes to this table)
     - Identify downstream consumers (who reads from this table)
1.4  Log all discovered references
```

### Step 2 — Build DAG (NetworkX)

```
2.1  Create directed graph G
2.2  Add nodes for every object in inventory:
     - node attributes: id, name, type, database, classification
2.3  Add edges for every dependency:
     - edge attributes: type (data_flow, control_flow, reference), weight
2.4  Validate graph structure
2.5  Log node and edge counts
```

### Step 3 — Detect Cycles

```
3.1  Run cycle detection algorithm on G
3.2  If cycles found:
     - Log each cycle with participating nodes
     - Flag as WARNING in output
     - Suggest resolution strategies
3.3  If no cycles: confirm DAG validity
```

### Step 4 — Calculate Graph Metrics

```
4.1  Calculate metrics:
     - Total nodes and edges
     - Max depth (longest path)
     - Average degree (in/out)
     - Connected components count
     - Isolated nodes (no connections)
     - Hub nodes (highest degree)
     - Critical path (longest dependency chain)
4.2  Identify root nodes (no incoming edges — sources)
4.3  Identify leaf nodes (no outgoing edges — sinks)
4.4  Calculate topological sort order (migration sequence)
```

### Step 5 — Generate Output

```
5.1  Export graph to dependency-graph.json
5.2  Include:
     - Full node and edge lists
     - Cycle warnings
     - Graph metrics
     - Topological sort order
     - Recommended migration sequence
5.3  Save to projects/{project_name}/outputs/upstream/discovery/dependency-graphs/
```

---

## Error Handling

| Error                        | Action                                          |
|------------------------------|--------------------------------------------------|
| Unparseable SQL              | Log warning, add edge as UNKNOWN type            |
| Circular dependency          | Log cycle, flag in output, do NOT remove edges   |
| Missing referenced object    | Create phantom node, flag as EXTERNAL            |
| Ambiguous reference          | Log all candidates, mark as AMBIGUOUS            |

- [ ] Cycle detection completed

## Detecção de Acoplamento Cross-Tecnologia por Filesystem

Quando `scan_metadata.platform` = "Generic Spark / Mixed Code" (e como verificação
complementar em QUALQUER plataforma), aplicar as regras de
`mixed-pipeline-coupling-patterns.md` para detectar dependências que não passam
por nenhuma API de orquestração:

### Padrões de detecção obrigatórios

1. **Flag files** — script A escreve arquivo sentinela (open/write de path com
     "flag", "ok", "done", ".lock"); script B testa existência do mesmo path
     (os.path.exists, File.exists, IF EXIST). Registrar como:
     `A → B (mechanism: FLAG_FILE, path: <path>)`

2. **Artefatos de dados intermediários** — componente A escreve CSV/parquet/txt
     em path X; componente B lê do mesmo path X (spark.read, open, BULK INSERT,
     OPENROWSET). Registrar como:
     `A → B (mechanism: DATA_FILE, path: X, format: <fmt>)`
     Normalizar paths antes de comparar (case-insensitive em Windows, resolver
     variáveis óbvias tipo $PMBadFileDir).

3. **BULK INSERT / LOAD reverso** — procedure SQL importando arquivo gravado por
     Python/Scala fecha ciclos cross-tecnologia. SEMPRE verificar se o path do
     BULK INSERT aparece como write target em outro componente do inventário.

4. **Dependências temporais implícitas** — Thread.sleep, time.sleep em loop de
     espera, agendamentos com horário fixo em sequência. Registrar como:
     `A → B (mechanism: TEMPORAL_ASSUMPTION, detail: <sleep/schedule>)`
     e marcar FRAGILE — não há garantia real de ordem.

5. **Dependências externas** — linked servers (nomes 4-part ou IP), connection
     strings para hosts fora do repositório, chamadas HTTP. Registrar como:
     `EXTERNAL → A (mechanism: LINKED_SERVER | EXTERNAL_DB | HTTP, target: <host>)`
     Estes objetos NÃO estão no repo mas quebram o pipeline se mudarem.

### Regra de ouro

Toda aresta do grafo DEVE registrar o `mechanism` do acoplamento — a modernização
para Databricks converte cada mecanismo de forma diferente:
FLAG_FILE/TEMPORAL → task dependency declarativa (o artefato desaparece);
DATA_FILE → passagem direta de DataFrame ou tabela Delta;
LINKED_SERVER → Lakehouse Federation ou ingestão CDC.
